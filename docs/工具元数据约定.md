# 工具元数据约定（TOOL 与 PLUGIN）

> 2026-09-20 立。起因：实测发现 **22 个工具只写 `PLUGIN`、20 个只写 `TOOL`**，
> 而"关键词自动路由"只读 `TOOL.keywords` —— 于是那 22 个工具的关键词**一直是死的**，
> 没有任何报错、也没有任何提示（沉默的失效配置最贵）。

---

## 一、两个块各管什么

| 块 | 谁在读 | 作用 |
|----|--------|------|
| `TOOL = {name, description, keywords, params, ...}` | `core/plugin_manager.py::match_keywords`、`core/tool_schema.py`、`core/pipeline.py::_match_keywords` | **参与关键词自动路由**；并生成给模型的工具 schema |
| `PLUGIN = {name, description, trigger, permission, category, ...}` | `core/tool_schema.py`（兼容读取） | 元数据/归类/权限声明；**不参与关键词路由** |

## 二、关键词路由的语义（重要）

关键词命中后**不是提示模型**，而是**直接执行该工具**，并把
`query = 原消息去掉命中的关键词` 作为参数传进去
（`core/pipeline.py::_run_plugin_keyword`）。

因此：

- 关键词要**具体**（`收邮件` 可以，`邮件` 太泛，`运行/执行/命令` 属于危险泛词 ——
  一旦被路由就会**直接跑 shell**）。
- `file_ops` 与 `shell_exec` 已被硬性排除在关键词路由之外（它们需要精确的
  action+path/cmd，靠 `query=` 会传错参数）。
- 想让一个工具的关键词生效 → **必须写 `TOOL.keywords`**；只写 `PLUGIN.trigger`
  等于没写（本机曾有 16 个工具处于这种状态）。

## 三、新工具怎么写（推荐）

```python
TOOL = {
    "name": "my_tool",
    "description": "一句话说清它干什么（会进模型可见的工具表）",
    "keywords": ["具体说法1", "具体说法2"],     # 只有这里的关键词会参与路由
    "params": [{"name": "action", "type": "str", "required": True, "description": "..."}],
}
PLUGIN = {                                     # 兼容旧读法，建议同步写
    "name": "my_tool", "description": "同上", "version": "1.0",
    "trigger": ["与 TOOL.keywords 保持一致"],
    "permission": ["read"], "category": "productivity",
}
```

两处的 `name` **必须一致**（门禁会查）。

## 四、登记（否则工具会被安全扫描拒绝加载）

新工具必须在 `config/settings.py` 的 `SAFE_PLUGINS` 里登记 ——
`PluginManager._load_plugins()` 对**未登记**的模块做 AST 静态扫描，
凡 `import os / subprocess / socket / ctypes / requests` 一律拒绝加载，
调用方只会看到"未知工具: xxx"（2026-09-20 实测：`vision` / `image_gen` / `backup`
三个工具因此静默失效，而失败提示还把病因说成"凭证问题"）。

门禁：`python scripts/verification/verify_tool_registry.py`
- `[A]` 无工具被静默拒绝
- `[B]` 实际加载面 = 磁盘面
- `[D]` 两处白名单同源
- `[F]` 关键词元数据一致性（会点名"写了 trigger 却无效"的工具）

## 五、当前状态（门禁 `[F]` 段每次都会重报，并**逐工具给出理由**）

```text
(以下数字由 verify_tool_registry.py 的 [F] 段实测输出, 2026-09-21 复核)
写 TOOL.keywords 且写 PLUGIN.trigger :  4 个
只写 TOOL.keywords（可被路由）        : 15 个
只写 PLUGIN.trigger（关键词不生效）   : 12 个
两处都没有                            :  6 个
```

## 六、这 18 个工具**该不该**补 `TOOL.keywords` —— 定论：**不补**（2026-09-21）

判据两条，缺一不可：

```text
① 有没有**技能**在做它的用户入口？
   技能里的 `requires_tools:` 声明了它 → 那个技能就是它的用户入口。
   补 TOOL 块 = 关键词**直接执行**工具 → **绕过技能层**
   （技能里有 LLM 兜底 / 缺参反问 / 结果润色）→ 输出反而更差。
   查法:  grep -rn "requires_tools" tmm_skills/*/SKILL.md

② 关键词命中后**只靠 query** 能跑对吗？
   query 只带"去掉关键词的残句"。需要精确参数的工具（to/subject/body/cmd/文件名）
   补不了这些参数 → 命中后要么报错、要么做错事。
```

实测结论（12 个"只写 trigger" + 6 个"两处都没有"）：

| 工具 | 谁在做用户入口 | 结论 |
|------|----------------|------|
| check_mail | 技能 inbox-triage | 不补（补了会绕过技能层） |
| github_api | 技能 github-issues | 不补 |
| send_email | 技能 send-email-to-contact / send-file-to-contact | 不补 |
| service_check | 技能 healthcheck | 不补 |
| session_logs | 技能 session-logs | 不补 |
| usage_stats | 技能 model-usage | 不补 |
| voice | 技能 speak-aloud | 不补 |
| tiger_office | 15 个技能（write-*/make-slides/table-to-report…） | 不补 |
| whisper | 技能 transcribe-audio / video-summarize | 不补 |
| **file_ops / shell_exec** | ★ `core/pipeline.py` 已**硬排除**在关键词路由之外 | 更不能补（泛词危险） |
| im_notify / push_notify / sms_send | 无技能入口 | 不补（需要 to/subject/body） |
| hermes_bridge / office_cli / win32_input / windows_desktop / web_search | 无技能入口 | 交模型按名调用（web_search 另有 Brain 硬编码路由） |

★ 门禁 `[F]` 的措辞本身也修了（2026-09-21）：原来只写
"想让关键词生效需补 TOOL 块" —— 那是在**指错方向**，照做会把
"沉默的死配置"换成"绕过技能层的劣质路由"。现在门禁逐工具打印上面这张判定表，
并且**每次断言** `file_ops`/`shell_exec` 的硬排除判据仍在位（带变异自检，防空转）。
